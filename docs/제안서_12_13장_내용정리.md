# 12장. CCTV 영상 기반 교통상황 판단 기능

## 12.1 현황 및 문제

### 현행 상황 판단 프로세스

현재 교통상황실에서는 사고 발생 시 상황근무자가 CCTV 영상을 육안으로 확인하여 정체길이, 차단 유형, 관련 차량 등을 판단하고 있다.

### 문제점

| 문제 | 설명 |
|------|------|
| **근무자 주관성** | 같은 현장을 보고도 판단자에 따라 정체길이, 차단 범위, 심각도 평가가 다를 수 있음 |
| **판단 편차** | 교대 근무, 피로도, 경험 차이에 의해 동일 상황에서도 대응 수준이 달라짐 |
| **확인 지연** | 다수 CCTV 중 사고 현장 인근 카메라를 수동으로 찾고 전환하는 데 시간 소요 |
| **기록 비정형** | 판단 결과가 구두 보고나 자유 서술로 전달되어 체계적 축적이 어려움 |

> *"사고발생 시 CCTV 영상 확인을 통한 정체길이 판단 및 대응 — 근무자의 주관성 및 정확도 측면에서 편차 발생"*
> — 사업계획서 1장

---

## 12.2 해결 방안 개요

ITS 돌발정보 시스템과 연동하여, 사고가 발생하면 **인근 CCTV를 자동으로 찾아 영상을 수집**하고, **AI가 영상을 분석하여 교통상황을 객관적으로 판단**하는 시스템을 구축한다.

```
기존: 사고 접수 → 근무자가 CCTV 수동 탐색 → 육안 판단 → 구두 보고

개선: 사고 접수 → CCTV 자동 연결 → AI 영상 분석 → 구조화 보고서 자동 생성
```

핵심 변화: **"사람이 찾아서 보고 판단"** → **"시스템이 찾아서 AI가 판단"**

## 12.3 핵심 기술

### (1) ITS 돌발정보 연동 — 자동 CCTV 연결

ITS 국가교통정보센터의 돌발상황 정보를 실시간으로 수신하여, 사고/고장이 감지되면 해당 위치 인근 CCTV에 자동으로 접속한다.

| 항목 | 내용 |
|------|------|
| 연동 대상 | ITS 돌발상황 API (its.go.kr) |
| 감지 유형 | 사고, 고장, 낙하물 등 |
| CCTV 검색 | 돌발 위치 기준 인근 CCTV 자동 순회 |
| 수집 주기 | 60초 간격 폴링 |

기존에는 근무자가 돌발정보 접수 후 CCTV를 수동으로 찾아야 했으나, 본 시스템은 돌발정보 수신 즉시 인근 CCTV에 자동 접속하여 **사고 인지-영상 확인 사이의 지연을 해소**한다.

### ITS CCTV 화상자료 API 인터페이스

ITS 국가교통정보센터에서 제공하는 CCTV 화상자료 Open API를 활용하여, 좌표 범위 기반으로 CCTV 목록과 스트리밍 URL을 조회한다.

**요청 변수**

| 요청변수 | Type | 조건 | 설명 |
|----------|------|------|------|
| apiKey | string | 필수 | 발급받은 인증키 |
| type | string | 필수 | 도로 유형 (ex: 고속도로 / its: 국도) |
| cctvType | string | 필수 | CCTV 유형 (1: 실시간 스트리밍 HLS / 2: 동영상 mp4 / 3: 정지 영상 / 4: 실시간 스트리밍 HLS(HTTPS) / 5: 동영상 mp4(HTTPS)) |
| minX | double | 필수 | 최소 경도 영역 |
| maxX | double | 필수 | 최대 경도 영역 |
| minY | double | 필수 | 최소 위도 영역 |
| maxY | double | 필수 | 최대 위도 영역 |
| getType | string | 필수 | 출력 결과 형식 (xml, json / 기본: xml) |

**출력 변수**

| 출력변수 | Type | 설명 |
|----------|------|------|
| coordtype | string | 좌표타입 |
| datacount | int | CCTV 개수 |
| roadsectionid | string | 도로 구간 ID |
| filecreatetime | string | 파일 생성 시간 (YYYYMMDDHH24MISS) |
| cctvtype | string | CCTV 유형 (1~5) |
| cctvurl | string | CCTV 영상 주소 |
| cctvresolution | string | CCTV 해상도 |
| coordx | string | 경도 좌표 |
| coordy | string | 위도 좌표 |
| cctvformat | string | CCTV 형식 |
| cctvname | string | CCTV 설치 장소명 |

본 사업에서는 `type=ex`(고속도로), `cctvType=1`(HLS 실시간 스트리밍)을 기본으로 사용하며, 응답의 `cctvurl`로 HLS 스트림에 직접 접속하여 영상을 수집한다. `coordx`, `coordy`는 CCTV-사고다발구간 자동 매칭의 기초 좌표로 활용된다.

### (2) CCTV-사고다발구간 자동 매칭

전국 고속도로 CCTV를 사고다발 1km 구간과 자동으로 매칭하여, **사고 영상을 확보할 확률이 가장 높은 CCTV**를 데이터 기반으로 선정한다.

| 항목 | 내용 |
|------|------|
| 전국 고속도로 CCTV | 4,749대 (ITS API 전수 조회) |
| 사고다발 1km 구간 | 1,093개 (35개 노선) |
| 매칭 방식 | IC/JCT 좌표 기준점 + 2D 세그먼트 사영(射影) 보간 |

**매칭 원리**:
1. ITS API에서 전국 CCTV 좌표(위경도)와 고속도로 IC/JCT 좌표를 수집
2. IC/JCT 간 선형 보간으로 각 CCTV의 노선 km를 추정
3. 사고다발구간(노선+km 범위)과 CCTV km를 대조하여 최근접 매칭
4. 사고 건수 기준으로 Tier 2 핫스팟 우선순위 산정

> 사전 검증(PoC)에서 1,093개 전 구간 매칭에 성공하였으며, 94.1%가 5km 이내 정확도를 달성하였다 (→ 13.7절 사전 기술 검증 참조).

### (3) 영상 수집 — 2모드 운용

사고 현장 CCTV 영상을 두 가지 방식으로 수집한다.

**모드 A: 체류형 캡처 (돌발 대응)**

사고 접수 즉시 인근 CCTV에 접속하여 단시간 프레임을 캡처한다.

| 항목 | 내용 |
|------|------|
| 체류 시간 | CCTV당 30초 |
| 캡처 속도 | 1fps (초당 1장) |
| 수집량 | CCTV 1대당 최대 30프레임 |
| 경과시간 추적 | 사고 접보 시각 대비 캡처 시점의 경과시간 자동 기록 |

**모드 B: 연속 녹화 (사고다발 구간 상시 감시)**

Tier 2 핫스팟 CCTV에서 **HLS 세그먼트 직접 다운로드** 방식으로 24시간 연속 녹화하여, 사고 발생 전후 영상을 확보한다. 사고다발구간에서 실제 사고 영상을 수집하기 위한 핵심 수단이다.

| 항목 | 내용 |
|------|------|
| 수집 방식 | Python m3u8 세그먼트 직접 다운로드 |
| 원리 | HLS master playlist → media playlist URL 추출 → m3u8 파싱 → .ts 세그먼트 HTTP GET → 단일 파일 append |
| 출력 포맷 | MPEG-TS (.ts), H.264, 720×480 |
| 세션 만료 대응 | ~5분마다 403 응답 시 내부적으로 세션 자동 재수립 (끊김 없이 녹화 지속) |
| 녹화 단위 | 24시간 연속, 카메라당 단일 파일 |
| 예상 데이터량 | 카메라당 ~10.8GB/일 (평균 ~1.2Mbps, 카메라별 0.6~2.2Mbps 편차) |

#### 방식 선정 배경: ffmpeg 대비 HLS 직접 다운로드의 우위

ITS CCTV HLS 프록시는 ~5분마다 세션이 만료되어 403 응답을 반환한다. 이 제약 하에서 두 방식을 비교 검토하였다.

| 비교 항목 | ffmpeg `-c copy` | HLS 직접 다운로드 (채택) |
|-----------|------------------|-------------------------|
| 세션 만료 대응 | 프로세스 crash → 외부 재시작 필요 | 내부 세션 자동 재수립, 녹화 지속 |
| 24시간 출력 | 카메라당 ~270개 프래그먼트 → 후처리 merge 필수 | **단일 파일** (후처리 불필요) |
| 무인 운용 | 워치독 프로세스 별도 필요 | 자체 재수립으로 무인 달성 |
| 끊김 | 세션 전환 시 수초 갭 발생 가능 | 끊김 없음 |

> **선정 결론**: ffmpeg 방식은 세션 만료 시 프로세스가 종료되어 24시간 연속 녹화에 부적합하다. HLS 직접 다운로드 방식은 세션 만료를 내부적으로 처리하며 단일 파일로 연속 기록하므로, 사고다발구간 상시 녹화에 적합하다.
>
> 사전 검증(PoC)에서 5대 동시 24시간 녹화를 수행하여 끊김 0건, 총 ~60GB 정상 수집을 확인하였다 (→ 13.7절 참조).

### (4) 3-Tier 전국 CCTV 감시 체계

전국 고속도로 CCTV **4,749대**를 3단계로 나누어 효율적으로 감시한다.

| Tier | 대수 | 역할 | 분석 방법 |
|------|------|------|----------|
| **Tier 1** (프리필터) | **4,749대** | 전국 광역 감시 | 경량 영상 변화 감지 (배경 차분) |
| **Tier 2** (핫스팟) | 50대 | 사고다발 구간 상시 정밀 | 차량 검출 + 추적 + 트리거 + HLS 연속 녹화 |
| **Tier 3** (정밀) | 동적 | 이상 감지 또는 사고 발생 구간 | 전체 AI 파이프라인 |

- Tier 1은 OpenCV 기반 경량 처리(프레임당 약 1.5ms)로 전국 카메라를 상시 감시
- Tier 2의 50대는 **CCTV-사고다발구간 자동 매칭** 결과에서 사고 건수 상위 구간의 CCTV로 선정
- 이상이 감지되면 해당 카메라를 Tier 3으로 승격하여 정밀 분석
- ITS 돌발정보로 사고가 확인되면 인근 CCTV를 Tier 3에 즉시 편입

이 구조를 통해 제한된 서버 자원으로 **전국 규모의 감시와 정밀 분석을 동시에 달성**한다.

### HLS 동시접속 제한과 운용 설계

ITS CCTV HLS 프록시는 API 키 1개당 동시 스트림 수를 제한한다. 초과 시 전체 403 차단이 발생하며, ~10분 쿨다운 후 자동 복구된다.

| 항목 | 내용 |
|------|------|
| API 키당 동시 스트림 | ~16-19대 |
| 초과 시 | 전체 403 차단 → ~10분 쿨다운 |

> Tier 2 핫스팟 50대를 동시 운용하려면 API 키 **3개 이상** 필요하며, Tier 3 동적 편입분을 고려하면 4개를 권장한다.

### CCTV 프로토콜 (cctvType)

ITS API는 CCTV 영상을 5가지 유형으로 제공한다.

| cctvType | 프로토콜 | 설명 | HLS 직접 접속 |
|----------|---------|------|--------------|
| 1 | HTTP HLS | 실시간 스트리밍 (HLS) | **정상** (기본 사용) |
| 2 | HTTP MP4 | 동영상 (mp4) | — |
| 3 | — | 정지 영상 | — |
| 4 | HTTPS HLS | 실시간 스트리밍 (HLS)(HTTPS) | 403 차단 (User-Agent 제한 추정) |
| 5 | HTTPS MP4 | 동영상 (mp4)(HTTPS) | — |

실운용 시 cctvType=1(HTTP HLS)을 기본으로 사용한다. cctvType=4(HTTPS HLS)는 ffmpeg/ffprobe에서 403 차단이 발생하나, 브라우저 기반 Playwright 캡처는 접근 가능하다.

### (5) 비전 파이프라인 — AI 기반 교통상황 분석

Tier 2/3에서는 YOLO 객체 검출과 ByteTrack 추적 기반의 비전 파이프라인이 실시간으로 교통상황을 분석한다.

**처리 단계**:

```
영상 프레임 입력
  → 차량 검출 (YOLO, 프레임당 21ms)
  → 차량 추적 (ByteTrack, 차량별 궤적 생성)
  → 속도 추정 (픽셀 이동량 기반)
  → 충돌시간(TTC) 계산 (차량 간 접근 속도)
  → 이상상황 트리거 판정 (7종)
```

**이상상황 트리거 7종**:

| 트리거 | 감지 대상 | 심각도 |
|--------|----------|--------|
| T1 | 충돌시간(TTC) 임박 | 높음 |
| T2 | 급감속 | 높음 |
| T3 | 비정차 구간 정차 | 보통 |
| T4 | 역주행 | 최고 |
| T5 | 다중 차량 동시 급감속 (3대 이상) | 최고 |
| T6 | 속도 분산 급증 | 보통 |
| T7 | 주기 상황 요약 (5분 간격) | 정보 |

트리거가 발생하면 해당 시점의 키프레임(핵심 장면 이미지)을 자동 선정하여 AI 분석 단계(13장)로 전달한다.

### (6) 프리필터 — 경량 이상 감지

Tier 1에서 YOLO 없이도 이상 프레임을 빠르게 감지하는 경량 엔진이다.

| 감지 방법 | 원리 |
|-----------|------|
| 배경 차분 (MOG2) | 전경 비율이 급변하면 이상 의심 |
| 프레임 차분 | 연속 프레임 간 변화량이 임계를 넘으면 이상 |
| 히스토그램 변화 | 화면 전체 밝기/색 분포가 급변하면 이상 |
| 정지 객체 | 비정차 구간에서 장시간 정지 객체 감지 |

처리 속도: 프레임당 약 1.5ms (640x480 기준). YOLO 대비 약 14배 빠른 처리로 다수 카메라의 동시 감시가 가능하다.

### (7) ITS 사고 반응기 — 자동 편입

ITS 돌발상황 API를 주기적으로 확인하여, 새로운 사고가 발생하면 인근 CCTV를 자동으로 Tier 3(정밀 분석)에 편입한다.

| 항목 | 내용 |
|------|------|
| 폴링 주기 | 60초 |
| 편입 CCTV 수 | 사고 1건당 인근 3대 |
| 유지 시간 | 편입 후 10분 (이후 자동 복귀) |

## 12.4 처리 흐름

### 전체 흐름도

```
[1] ITS 돌발정보 수신
     │
     ├─ 사고/고장 확인
     │
[2] 인근 CCTV 자동 연결
     │
     ├─ 모드 A: 체류형 캡처 (30초, 1fps) — 즉시 대응
     ├─ 모드 B: HLS 직접 다운로드 연속 녹화 — 사고다발 구간 상시
     │
[3] 영상 분석
     │
     ├─ Tier 1: 프리필터 (경량 이상 감지)
     │    └─ 이상 감지 시 → Tier 3 승격
     │
     ├─ Tier 2/3: 비전 파이프라인
     │    ├─ 차량 검출·추적
     │    ├─ 속도·TTC 계산
     │    └─ 이상상황 트리거 판정
     │
[4] AI 판단 (13장과 연결)
     │
     ├─ 대표 프레임 선정 (30장 → 5장)
     ├─ 멀티모달 AI 분석
     └─ 교통상황 보고서 자동 생성
```

### 사고 대응 시나리오 (예시)

1. **08:15** — ITS 돌발정보: 경부선 수원-오산 구간 사고 접수
2. **08:15** — 시스템이 인근 CCTV 3대에 자동 접속, 체류 캡처 시작. Tier 2 핫스팟 CCTV는 이미 HLS 연속 녹화 중이므로 **사고 발생 전 영상도 확보**
3. **08:16** — 30초간 총 90프레임(3대 x 30프레임) 캡처 완료
4. **08:16** — 비전 파이프라인이 정차 차량, 차로 차단 감지
5. **08:16** — 대표 프레임 5장 선정 → 멀티모달 AI 분석 시작
6. **08:17** — AI가 차단 유형(부분차단), 관련 차량(승용차+화물차), 기상(맑음) 등 판단
7. **08:17** — 구조화된 보고서 자동 생성 → DB 적재

기존 방식 대비 **CCTV 탐색 ~ 상황 보고까지 소요 시간: 약 2분** (기존: 수동 탐색 + 판단에 5~10분 이상)

# 13장. 영상 기반 생성형 AI 모델 및 검증

## 13.1 8~11장(텍스트 LLM)과의 관계

8~11장에서는 **Gemma3 텍스트 LLM**이 사고 보고서, 접보 문자, 사고 조서 등 **텍스트 데이터**를 분석하여 정형 DB를 구축한다. 본 장에서는 **멀티모달 VLM(Vision-Language Model)**이 **CCTV 영상 데이터**를 직접 분석하여 정형 DB를 구축한다.

| 구분 | 8~11장 (텍스트 LLM) | 12~13장 (영상 VLM) |
|------|---------------------|---------------------|
| **입력** | 사고 보고서 텍스트 | CCTV 영상 프레임 |
| **AI 모델** | Gemma3 (텍스트 전용) | Qwen2.5-VL (영상+텍스트 동시 이해) |
| **분석 대상** | 접보 내용, 사고 경위, 피해 상황 서술 | 현장 영상: 차량, 차로, 기상, 파손 상태 |
| **장점** | 상세 서술 정보 추출 (원인, 경위, 인명피해) | 즉시 가용, 현장 시각 정보 직접 판독 |
| **한계** | 보고서 작성까지 시간 소요 | 인명피해 등 비시각 정보 판단 불가 |
| **출력** | 정형 DB (사고 특성, 원인, 피해) | 정형 DB (현장 상황, 차량, 차로, 시설물) |

### 상호 보완 관계

```
사고 발생
  │
  ├── [즉시] CCTV 영상 → 멀티모달 VLM → 현장 시각 정보 자동 추출
  │    (기상, 차단유형, 차량대수/차종, 차로피해, 화재/전복 여부)
  │
  └── [이후] 사고 보고서 → 텍스트 LLM → 상세 사고 정보 추출
       (사고원인, 경위 서술, 인명피해, 처리시간, 견인/119 정보)
```

- **영상 VLM이 먼저** 사고 현장의 시각적 정보를 즉시 추출 (사고 접수 후 약 2분)
- **텍스트 LLM이 이후** 사고 보고서가 작성되면 상세 정보를 보완
- 14장에서 두 채널의 결과를 통합하여 **완전한 사고 DB**를 구축

이 구조를 통해 **사고 직후에는 영상 기반 속보성 정보**를, **보고서 완성 후에는 텍스트 기반 상세 정보**를 확보하여, 시간 축을 따라 사고 정보가 점진적으로 풍부해지는 체계를 갖춘다.

## 13.2 멀티모달 AI 모델

### 모델 선정

CCTV 영상을 직접 이해할 수 있는 멀티모달 VLM(Vision-Language Model) Qwen2.5-VL을 사용한다.

| 항목 | 내용 |
|------|------|
| 모델명 | Qwen2.5-VL-3B-Instruct |
| 모델 유형 | 멀티모달 VLM (이미지+텍스트 동시 입력/출력) |
| 파라미터 | 약 30억 개 |
| 추론 환경 | CPU 서버 (GPU 없이 운용 가능) |
| 프레임워크 | HuggingFace Transformers |
| 한국어 지원 | 학습 데이터에 한국어 포함 |

### 기존 텍스트 LLM과의 차이

| 구분 | 텍스트 LLM (Gemma3) | 멀티모달 VLM (Qwen2.5-VL) |
|------|---------------------|---------------------------|
| 입력 | 텍스트만 | 이미지 + 텍스트 동시 |
| 영상 직접 분석 | 불가 | **가능** |
| CCTV 프레임 판독 | 불가 | **가능** (차량, 도로, 기상 등 직접 인식) |
| 적합 용도 | 사고 보고서 텍스트 분석 | 사고 현장 CCTV 영상 분석 |

### 왜 멀티모달 VLM이 필요한가

CCTV 영상에는 텍스트로 변환되지 않은 정보가 풍부하다:
- 차량의 파손 상태, 전복/전도 여부
- 차로 차단 범위 (전면/부분/갓길)
- 화재, 적재물 유출 여부
- 도로 시설물(가드레일, 중분대 등) 피해
- 기상 상태 (맑음, 비, 눈, 안개)

이러한 정보는 사고 보고서가 작성되기 전, CCTV 영상에서 즉시 확인할 수 있는 항목이다. 멀티모달 VLM은 이 영상 정보를 AI가 직접 판독하여 구조화된 데이터로 변환한다.

### GPU 확장 설계

현재는 CPU 환경에서 경량 모델(3B)로 운용하되, GPU 도입 시 대형 모델로 교체하여 분석 품질과 속도를 향상시킬 수 있도록 설계하였다.

| 항목 | 현재 (CPU) | GPU 도입 시 |
|------|-----------|------------|
| 모델 크기 | 3B | 72B (24배) |
| 추론 시간 | 약 50~70초/건 (실측 59초) | 1~3초/건 |
| 전환 방법 | API 엔드포인트 변경만으로 교체 가능 |

모델 교체 시 프롬프트와 출력 형식은 동일하게 유지되므로, 하위 시스템(DB 적재, 보고서 생성) 변경 없이 모델만 교체할 수 있다.

## 13.3 출력 설계 — 도공 보고서 양식 매핑

### 프롬프트 설계 원칙

멀티모달 VLM의 프롬프트는 한국도로공사 전면차단 사고 보고서 실물 양식을 기반으로 설계하였다. AI의 출력이 기존 업무 양식과 직접 대응되도록 하여, 추가 변환 없이 보고서 항목을 채울 수 있다.

### AI 분석 출력 항목

CCTV 영상 분석 시 AI가 자동으로 추출하는 항목은 다음과 같다:

| 분류 | 출력 항목 | 설명 |
|------|----------|------|
| **환경** | 기상 | 맑음, 흐림, 비, 눈, 안개 |
| **사고 유형** | 차단 유형 | 전면차단, 부분차단, 갓길 |
| | 차단 차로 | 피해 차로 번호 목록 |
| | 차로 수 | 해당 구간 총 차로 수 |
| | 도로 선형 | 직선, 곡선, 터널, 교량 |
| **관련 차량** | 차량 대수 | 사고 관련 차량 수 |
| | 차종 | 승용차, 화물차, 버스, 승합차, 이륜차, 특수차 |
| | 크기 | 소형, 중형, 대형 |
| | 적재물 | 적재물 종류 (해당 시) |
| | 파손 상태 | 파손, 전복, 전도, 정차 등 |
| **부가 상황** | 화재 여부 | 화재 발생 유무 |
| | 전복/전도 | 차량 전복·전도 여부 |
| | 적재물 유출 | 유출 여부 및 유형 |
| | 시설물 피해 | 가드레일, 중분대, 방음벽, 표지판 등 |
| **AI 추론** | 사고원인 추정 | 주시태만, 졸음운전, 과속, 안전거리미확보 등 |
| | 경위 서술 | 사고 상황 서술 (3~5문장) |
| | 심각도 | 경미, 보통, 중대, 심각 |
| | 신뢰도 | AI 판단의 자체 신뢰도 (0~1) |

### CCTV 판단 가능/불가능 구분

사고 보고서 전체 항목 중 CCTV 영상에서 AI가 판단할 수 있는 항목과 현장 확인이 필요한 항목을 명확히 구분한다.

| 구분 | 항목 예시 | 비율 |
|------|----------|------|
| **AI 자동 생성** | 접보시각, 위치, 기상, 사고유형, 차단유형, 관련차량, 차로피해 | 약 27% |
| **AI 추정 (참고용)** | 인명피해 수준, 심각도, 화재/전복 여부 | 약 8% |
| **현장 확인 필수** | 순찰대 도착시각, 견인 시각, 소통재개 시각, 도로/시설물 피해 상세 | 약 65% |

AI가 사고 직후 전체 보고서의 약 27%를 즉시 채우고, 현장 대응자가 나머지를 보완하는 구조이다. 이를 통해 **사고 보고의 초기 속도를 높이면서도 정확도를 확보**한다.

### 구조화 출력 (JSON)

AI의 응답은 자유 서술이 아닌 **정의된 JSON 형식**으로 강제한다. 이를 통해:
- 출력 결과를 DB에 직접 적재할 수 있음
- 항목 누락이나 형식 오류를 자동 검증할 수 있음
- 기존 보고서 양식과 1:1 매핑이 가능함

## 13.4 대표 프레임 선정

CCTV 체류 캡처로 수집된 30프레임 중 AI 분석에 가장 적합한 5프레임을 자동으로 선정한다.

### 선정 방법

히스토그램 거리(Bhattacharyya distance) 기반으로, 프레임 간 시각적 변화가 큰 장면을 우선 선택한다.

| 단계 | 내용 |
|------|------|
| 1 | 전체 30프레임의 밝기 히스토그램 계산 |
| 2 | 연속 프레임 간 히스토그램 거리(변화량) 산출 |
| 3 | 변화량이 큰 프레임을 우선 선택 (장면 전환 포착) |
| 4 | 첫 프레임과 마지막 프레임을 필수 포함 (시간 범위 확보) |
| 5 | 최종 5프레임 선정 → AI 분석 입력 |

### 선정 효과

- 30프레임을 모두 AI에 입력하면 추론 시간이 과다 소요
- 5프레임으로 압축하되, 장면 변화가 큰 핵심 프레임을 선택하여 **정보 손실을 최소화**
- 사고 전/중/후의 변화를 포착할 수 있는 시간 분포 확보

## 13.5 DB 적재

### DB 구조

분석 결과는 DuckDB 데이터베이스에 자동 적재된다. 사고 이벤트 테이블은 총 35개 컬럼으로 구성된다(스키마 정의 기준; 초기 운영 DB는 기본 24컬럼이며 마이그레이션으로 돌발정보 전용 11컬럼이 추가되어 35컬럼으로 확장된다).

| 컬럼 그룹 | 주요 컬럼 | 컬럼 수 |
|-----------|----------|---------|
| 기본 정보 | 이벤트ID, 영상ID | 2 |
| 위치 | 노선명, 방향, 이정, 관할지사, 사고지점유형 | 5 |
| 시간 | 접보시각, 생성시각 | 2 |
| 사고 특성 | 기상, 접보유형, 사고유형, 사고원인, 화재, 전복, 유출 등 | 8 |
| 피해 | 관련차량(JSON), 인명피해(JSON), 차로피해(JSON), 정체길이 | 4 |
| AI 분석 | 심각도, MLLM응답ID, MLLM보고서(JSON), 보고서경로 | 4 |
| 돌발정보 전용 | 차단유형, 경위서술, 시설물피해, 경과시간, 신뢰도 등 | 10 |
| **합계** | | **35** |

### 적재 흐름

```
체류 캡처 완료 (30프레임)
  → 대표 5프레임 선정
  → 멀티모달 VLM 분석 (JSON 응답)
  → 결과 검증 (필수 항목 확인, 기본값 보완)
  → analysis.json 파일 저장 (원본 보존)
  → DuckDB accidents 테이블 INSERT
```

### 비동기 처리

영상 수집과 AI 분석은 비동기 큐로 분리하여, 수집이 분석을 기다리지 않고 다음 CCTV로 넘어갈 수 있도록 설계하였다.

```
[수집 스레드]                      [분석 스레드]
체류 캡처 완료 → 큐에 추가    →    큐에서 꺼내기
다음 CCTV 이동                     MLLM 분석
                                    DB 적재
```

이를 통해 다수 CCTV의 수집과 분석을 병렬로 처리할 수 있다.

## 13.6 E2E (End-to-End) 처리 흐름

전체 시스템의 입력부터 출력까지 흐름을 정리한다.

```
[입력]
ITS 돌발정보 수신 (사고/고장)
  │
[CCTV 자동 연결]
  ├─ 인근 CCTV 검색 (위치 기반 + CCTV-사고구간 매칭 DB 활용)
  ├─ 모드 A: 체류 캡처 시작 (30초, 1fps)
  ├─ 모드 B: Tier 2 핫스팟은 HLS 직접 다운로드로 이미 연속 녹화 중
  └─ 프레임 저장 + 메타데이터(metadata.json) 기록
  │
[AI 분석]
  ├─ 대표 프레임 선정 (30장 → 5장, 히스토그램 기반)
  ├─ 멀티모달 VLM 추론 (Qwen2.5-VL, CPU)
  └─ 도공 보고서 양식 JSON 출력
  │
[출력]
  ├─ analysis.json 저장 (프레임과 함께 보존)
  └─ DuckDB 자동 적재 (35컬럼 accidents 테이블)
```

### HLS 직접 다운로드 연속 녹화

5개 노선 사고다발구간 CCTV 5대를 동시에 24시간 연속 녹화하여 방식의 안정성을 검증하였다.

| 끊김 | **0건** (세션 만료 시 자동 재수립) |
| 출력 | 카메라당 단일 .ts 파일 (후처리 불필요) |

### CCTV-사고다발구간 자동 매칭

전국 4,749대 CCTV를 1,093개 사고다발구간에 자동 매칭하여 정확도를 검증하였다.

| 항목 | 결과 |
|------|------|
| 매칭 대상 | 4,749대 CCTV ↔ 1,093개 구간 |

### 이상상황 감지 정밀도 (트리거 시스템)

트리거 정밀도를 단계적으로 개선하여 오탐을 대폭 감소시켰다.

| 지표 | 초기 v3 (실측) | 개선 v4 (설계 목표) | 기대 개선율 |
|------|-----------|-------------|--------|
| 시간당 트리거 | 약 285건 | 약 42건 | 85% 감소 |
| 시간당 TTC 오탐 | 약 254건 | 약 12건 | 95% 감소 |
| 오탐 녹화 | 6건 (전부 오탐) | 0건 | 100% 해소 |

> **측정 단서**: v3 수치는 51분·4카메라 모니터링 실측값이다. v4 수치는 개선 파라미터
> (TTC 2.0초·연속 4프레임·다중 합의)를 코드에 적용한 후의 **설계 목표(예상치)**이며,
> 동일 조건 재측정으로 확정 예정이다. 재현율(실제 사고 검출률)은 별도 검증이 필요하다.

**핵심 개선 3중 방어 계층** (코드 적용 완료):
1. 차선 필터: 동일 차선 차량 쌍만 TTC 계산 (교차 차선 오탐 제거)
2. 임계값 강화: TTC 2.0초, 연속 4프레임, 최소 TTC 0.5초, 쿨다운 60초
3. 다중 합의: 2종 이상 트리거 동시 발화 시에만 경보 (단독 TTC 차단)

### AI 분석 출력 필드 커버리지

| 구분 | 항목 수 | 비율 | 설명 |
|------|---------|------|------|

## 13장 슬라이드 시각자료

### [시각 13-1] 텍스트 LLM vs 멀티모달 VLM 상호 보완도

중앙에 "사고 DB"를 두고, 좌측에서 텍스트, 우측에서 영상이 합류하는 구조.

```
        텍스트 경로 (8~11장)              영상 경로 (12~13장)
        ────────────────                 ────────────────

     ┌──────────────┐                ┌──────────────┐
     │ 사고 보고서   │                │  CCTV 영상    │
     │ (원클릭 등)   │                │  (실시간)     │
     └──────┬───────┘                └──────┬───────┘
            ▼                               ▼
     ┌──────────────┐                ┌──────────────┐
     │   Gemma3     │                │ Qwen2.5-VL   │
     │  텍스트 LLM  │                │ 멀티모달 VLM  │
     └──────┬───────┘                └──────┬───────┘
            │                               │
            │  원인, 경위, 인명피해,          │  기상, 차량, 차로,
            │  처리시간, 견인정보             │  화재/전복, 시설물피해
            │                               │
            ▼                               ▼
        ┌───────────────────────────────────────┐
        │            통합 사고 DB                 │
        │         (DuckDB 35컬럼)                │
        │                                        │
        │   텍스트 분석 결과 + 영상 분석 결과      │
        │   → 완전한 사고 정형 데이터              │
        └────────────────────────────────────────┘
```

**용도**: 13장 슬라이드 메인 비주얼. Gemma3과의 관계를 명확히 보여주는 핵심 그림.
**강조점**: "경쟁이 아닌 보완" — 두 AI가 서로 다른 입력으로 같은 DB를 풍부하게 만듦.

### [시각 13-2] E2E 파이프라인 흐름도

좌→우 가로 흐름. 5단계를 아이콘+설명으로 표현.

```
┌──────────┐    ┌──────────┐    ┌──────────┐    ┌──────────┐    ┌──────────┐
│ ① ITS    │    │ ② CCTV   │    │ ③ 프레임 │    │ ④ VLM    │    │ ⑤ DB    │
│ 돌발정보  │───▶│ 체류캡처  │───▶│ 선정     │───▶│ 분석     │───▶│ 적재    │
│          │    │          │    │          │    │          │    │          │
│ 사고/고장 │    │ 30초     │    │ 30장→5장 │    │ Qwen2.5  │    │ 35컬럼  │
│ 자동 감지 │    │ ×1fps    │    │ 히스토그램│    │ -VL 추론 │    │ 자동    │
│          │    │ 30프레임  │    │ 기반선별  │    │ ~60초    │    │ INSERT  │
└──────────┘    └──────────┘    └──────────┘    └──────────┘    └──────────┘
```

**용도**: 13장 기술 흐름 설명 구성도.

### [시각 13-3] MLLM 입출력 예시

좌측에 CCTV 캡처 이미지 (전면차단 샘플.hwp의 BIN0004 사고촬영 사진 활용), 우측에 AI 출력 JSON을 시각화.

```
┌────────────────────┐         ┌──────────────────────────────┐
│                    │         │  AI 분석 결과                  │
│   [CCTV 사고영상]   │         │                              │
│                    │  ──▶    │  기상: 맑음                    │
│   (실제 CCTV       │   VLM   │  차단: 전면차단 (1,2번 차로)    │
│    캡처 이미지)     │         │  차량: 화물차 1대 (1톤 탑)      │
│                    │         │  적재물 유출: 의류원단          │
│                    │         │  시설물: 가드레일 파손          │
│                    │         │  원인: 차량결함 (타이어 파손)    │
│                    │         │  심각도: 보통                   │
│                    │         │  신뢰도: 0.72                  │
└────────────────────┘         └──────────────────────────────┘
```

**용도**: "AI가 실제로 무엇을 하는지" 직관적으로 보여주는 Before→After.
**이미지 출처**: `/공유폴더/파일공유용/JHJ/사고자료/전면차단 샘플.hwp` BIN0004 (CCTV 사고촬영 화면)

│  3. 기상  ██████████  AI 자동 (영상 판독)           │

### [시각 13-6] 비동기 수집-분석 병렬 처리도

두 스레드가 병렬로 작동하는 모습. 시간 축 위에 겹치는 구간 표시.

```
시간 →

수집 스레드:  [CCTV-A 캡처]──[CCTV-B 캡처]──[CCTV-C 캡처]──...
                  │                │
                  ▼ 큐             ▼ 큐
분석 스레드:       [A 분석→DB]──────[B 분석→DB]──────...

              ◀── 수집과 분석이 겹쳐서 전체 시간 단축 ──▶
```

**용도**: 기술 설명 보조. 다수 사고 동시 처리 가능성 강조.

## 부록: 용어 정리

| 용어 | 설명 |
|------|------|
| VLM (Vision-Language Model) | 이미지와 텍스트를 동시에 이해하는 AI 모델. CCTV 영상을 직접 보고 한국어로 분석 결과를 출력할 수 있다. |
| LLM (Large Language Model) | 텍스트만 처리하는 대규모 언어 모델. Gemma3이 이에 해당한다. |
| HLS (HTTP Live Streaming) | 비디오를 짧은 세그먼트(.ts)로 나누어 HTTP로 전송하는 스트리밍 프로토콜. ITS CCTV가 이 방식을 사용한다. |
| m3u8 | HLS 세그먼트 목록을 담은 재생목록 파일. master playlist와 media playlist로 구성된다. |
| TTC (Time to Collision) | 충돌까지 남은 시간. 앞차와의 거리와 접근 속도로 계산한다. |
| ByteTrack | 영상에서 차량을 프레임 간 연결하여 궤적을 추적하는 알고리즘 |
| MOG2 | 배경과 전경을 분리하는 알고리즘. 정상 배경을 학습하여 변화를 감지한다. |
| DuckDB | 분석용 경량 데이터베이스. 별도 서버 없이 파일 기반으로 동작한다. |
| ITS | 지능형교통체계 (Intelligent Transport Systems) |
| 3-Tier | 전국 CCTV를 3단계(광역감시-핫스팟-정밀)로 나누어 효율적으로 운용하는 구조 |
| 히스토그램 거리 | 두 이미지의 밝기/색상 분포 차이를 수치로 나타낸 것. 값이 클수록 장면이 크게 변했음을 의미한다. |
| nimblesessionid | ITS HLS 프록시의 세션 식별자. ~5분마다 만료되어 갱신이 필요하다. |
| 사영 보간 (射影 補間) | IC/JCT 좌표를 기준점으로 하여 CCTV 위치를 노선 km로 환산하는 2D 기하학적 보간 방법. |
